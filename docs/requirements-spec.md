## 1. 项目目标

用 DSH 在本机搭建一支「自媒体创作运营团队」，达成三个目标：

- **G1 闭环**：一条内容从选题到复盘，全流程可在本机自动跑通，人工只在关键节点做决策。
- **G2 分工**：Agent 负责编排、拆解、分配、控制；Skill 负责模块化执行。
- **G3 可观测**：数据库有记录、日志有留痕、页面能查看、能搜索、能分类。

### 1.1 成功判据（全部满足才算达标）

| ID   | 判据                                                              |
| ---- | --------------------------------------------------------------- |
| AC-1 | 一条真实选题可端到端产出：3 套文案 → 选定 1 套 → 24 格分镜 → 图片 → 视频 → 待发布状态         |
| AC-2 | 每个环节在核心业务表中都有对应记录                                               |
| AC-3 | 搭建过程报告页（build-log）与运营控制台（dashboard）均可在本机浏览器打开并正常交互             |
| AC-4 | 任一不可逆动作（对外发布、删除、外部写入）都有人工确认记录（`hitl_events`）                    |
| AC-5 | 每一步搭建都先通过模拟测试，才允许进入下一步                                          |
| AC-6 | 任一时刻可从《讨论记录》与《目录及文件说明》两份文档还原「做到哪、为什么这么做、还剩什么」                   |
| AC-7 | 结构或流程变更后，所有涉及的关系图/流程图同步更新且能通过 archify 校验                       |

## 2. 术语表（全文统一，不得混用）

| 术语      | 标识             | 定义                                                     | 禁止写法            |
| ------- | -------------- | ------------------------------------------------------ | --------------- |
| Agent   | `agent`        | 具备决策与编排能力的执行主体，可多个并存；负责拆解任务、分配、控制流程                    | 不写作「智能体」「机器人」混用 |
| Skill   | `skill`        | 单一职责的模块化执行单元，被 Agent 调用，一个 Skill 只做一件事                 | —               |
| 编排者     | `orchestrator` | 顶层 Agent，接收运营人员输入，决定调用哪些 Agent / Skill                | 不写作「管理者 Agent」  |
| 运营人员    | `manager`      | 真人操作者：做选择、审核、点发布                                       | 不写作「管理者」        |
| 产物      | `artifact`     | 流程中产生的文件或文本，登记在 `artifacts` 表                          | —               |
| 人工介入点   | `HITL`         | Human-in-the-loop，必须停下来等真人确认的节点                        | —               |
| 话题      | `topic`        | 一个选题条目，是内容生产的起点，可派生多条内容                                | 不写作「题目」「选题任务」混用 |
| 内容任务    | `task`         | 一个话题下的一次具体内容生产，对应一条流水线                                 | 不写作「工单」         |
| 搭建过程报告页 | `build-log 页面` | 记录搭建轨迹的 HTML 页面（位于仓库根目录）                               | 不要与运营控制台混称「页面」  |
| 运营控制台   | `dashboard`    | 日常管理任务的 HTML 页面（多页面）                                   | 同上              |
| 讨论记录    | `discussion-log` | 逐节点记录讨论内容、进度、确认事项与决策的文档（`docs/discussion-record.md`）  | 不写作「会议纪要」       |

> **关键消歧 1**：原始需求中的「管理者」有两种含义 —— 负责分配任务的 **Agent**，和做决策的 **真人**。
> 本文一律区分：Agent 侧称「编排者」，真人侧称「运营人员」。
>
> **关键消歧 2**：原始需求中的「热点」既可能是**选题来源**（做成内容），也可能是**数据分析对象**（只做汇总）。
> 本文一律区分：`FLOW-7` 是数据分析对象；源自热点的内容生产走 `FLOW-1`。

## 3. 讨论机制与留痕制度（可追溯，先固化）

原始需求明确：「为了不出现思想混乱的局面，讨论过程中要记录好每一次讨论节点内容、完成进度、剩余进度、确认落实的事项」，
且「把讨论方式本身固化成模板」。本章即该模板，**每次讨论必须按此执行**。

### 3.1 讨论记录文件

| ID      | 需求                                                                       |
| ------- | ------------------------------------------------------------------------ |
| R-D-01  | 讨论记录统一写在 `docs/discussion-record.md`，按节点递增编号 `N001`、`N002`…，编号一经使用不得复用      |
| R-D-02  | 每个节点必须固定包含 9 个字段（见 3.2），缺一不可                                             |
| R-D-03  | 同一节点被推翻或修订时，**不修改历史节点**，新增校正节点并在其中引用被校正节点编号                               |
| R-D-04  | 每次讨论结束后，必须回填：`本次结论`、`落实事项`（可执行动作列表）、`剩余进度`、`下次讨论前置条件`                  |

### 3.2 讨论节点模板（固定 9 字段）

| 字段         | 含义                                       |
| ---------- | ---------------------------------------- |
| 节点编号       | `N0NN`                                   |
| 日期时间       | 本地时间，精确到分钟                               |
| 讨论主题       | 一句话说清本次讨论什么                              |
| 背景与动机      | 为什么现在讨论这件事                               |
| 讨论内容       | 双方观点、被提方案、争议点，保留过程而不仅是结论                 |
| 本次结论       | 已达成的一致；无结论时明确写「未达成一致」                    |
| 落实事项（Action） | 可执行动作清单，每项带 `负责人 / 触发时机 / 验收方式`          |
| 完成进度       | 相对整体目标的百分比 + 已完成条目                       |
| 剩余进度       | 尚未完成的条目，与「完成进度」互补，二者合并应覆盖全部范围            |

### 3.3 进度台账

| ID     | 需求                                                                        |
| ------ | ------------------------------------------------------------------------- |
| R-D-05 | 维护一份总进度台账（见 §9），列出全部工作包、状态（未开始 / 进行中 / 已完成 / 已冻结）、当前节点编号、阻塞项 |
| R-D-06 | 台账状态只能在对应讨论节点中变更，页面或文档不允许出现无来源的状态                                  |

## 4. 总体架构：三层

| 层   | 名称     | 一句话目标           | 交付形态                                 |
| --- | ------ | --------------- | ------------------------------------ |
| L1  | 自动化闭环层 | 把内容生产流程跑通       | 流程 + Agent/Skill + 本地数据库             |
| L2  | 工程化实施层 | 有步骤、有记录、有文档、可回滚 | 实施步骤 + build-log 页面 + 文档 + GitHub 备份 |
| L3  | 人工运营层  | 让运营人员管得动        | 运营控制台多页面                             |

**实施顺序（不得颠倒）**：L1 设计冻结 → L1 环境与流程落地 → L2 边搭边记录 → L3 控制台接入。
L3 依赖 L1 的数据表结构，故必须在 L1 数据结构稳定后开工。

## 5. 第一层：自动化闭环（L1）

### 5.1 运行形态

| ID      | 需求                                                          |
| ------- | ----------------------------------------------------------- |
| R-L1-01 | 全部组件本地部署：流程自动化、数据查看页面、本地数据库。除必要外部服务（生图、生视频、平台上传）外不依赖云端    |
| R-L1-02 | 闭环范围：选题 → 文案 → 分镜图片 → 视频剪辑 → 分发 → 数据分析报告，首尾相接，无人工搬运断点    |

| R-L1-04 | 本地数据库文件与源码同仓，但数据库二进制文件（`*.db`）须在 `.gitignore` 中排除，仅入库结构与迁移脚本 |

### 5.2 分工机制

| ID      | 需求                                                                       |
| ------- | ------------------------------------------------------------------------ |
| R-L1-05 | 编排由 Agent 负责：接收需求 → 拆解任务 → 分配 → 控制流转 → 汇总结果                              |
| R-L1-06 | 允许同时存在多个 Agent（按环节或按角色划分）                                                |
| R-L1-07 | 具体执行由 Skill 承担；Skill 必须模块化、单一职责、可被单独调用与单独测试                              |
| R-L1-08 | 每个 Agent 与每个 Skill 都必须有 `README.md`，写清：用途、输入、输出、调用方式、依赖、示例、失败处理           |
| R-L1-09 | 命名规则：目录与文件名通俗易懂、见名知意（用完整英文单词，不用缩写黑话）；Skill 目录名用「动词-名词」形式，如 `generate-copy` |

> **命名例外**：行业已有公认拼写且更不易误解时，允许保留约定俗成的写法（如 `README.md`、`HITL`），
> 除此之外不使用缩写。例外项须登记在《目录及文件说明》中。

### 5.2.1 编排者 / Agent / Skill 三层边界（避免职责重叠）

| 层         | 只做                                       | 不做                             |
| --------- | ---------------------------------------- | ------------------------------ |
| 编排者 `orchestrator` | 接收运营人员输入、判定流程走向、决定调用哪个 Agent、汇总对外汇报、维护任务状态 | 不直接写文件、不直接调用外部 API、不做具体内容加工    |
| 环节 Agent  | 把一个环节内的多个 Skill 串起来，处理环节内的重试与失败分支       | 不跨环节调度、不修改其他环节的数据             |
| Skill     | 单一动作：输入 → 处理 → 输出，可独立测试                  | 不做流程判断、不决定下一步去哪里、不调用其他 Skill  |

> 判据：如果一段逻辑在决定「接下来做什么」，它属于 Agent；如果只是「把这件事做完」，它属于 Skill。

**编排者数量与职责（N002 定稿，S1）**：编排者有且仅有一个。它不并行处理多个环节的内部细节，只持有「任务当前状态 + 下一步该找谁」。
环节 Agent 建议 4 个：`copy-agent`（文案线）、`visual-agent`（视觉线）、`video-agent`（视频线）、`publish-agent`（分发与数据线）。

### 5.2.2 交接契约（S2：环节之间必须有校验点）

环节之间不允许「产出后直接往下跑」，必须通过交接契约：

| 环节出口      | 必须声明的三件事                    |
| --------- | --------------------------- |
| 输入校验      | 上一步的产物必须满足什么条件才允许本环节启动      |
| 产出物清单     | 本环节必须产出哪些文件/记录，数量与命名规则是什么   |
| 完成判据      | 什么情况下判定本环节成功，什么情况下退回上一步     |

**R-L1-18**：交接契约写在每个环节 Agent 的 `README.md` 中，并由对应技能在运行时校验；校验失败必须退回，不得带缺陷继续。
**R-L1-19**：典型校验例：分镜必须为 24 条且编号连续；图片必须 24 张且分辨率一致；文案必须 3 套且侧重点互不重复。
**R-L1-20**（N005 新增，依据实测）：每个 skill 目录固定三件套，文件名不得更改——
① `SKILL.md`：DSH 自动发现入口（工作区 `.dsh/skills/` 即 DSH 技能根目录）。必须为 YAML frontmatter + Markdown 正文；`name` 必须与目录名（= `skill_id`）一致；`description` 必须包含该 skill 的用途与「什么时候该用它」（决定编排者能否选中）；
② `README.md`：给人看的通俗说明，按 `docs/skill-readme-contract.md` 九段模板填写——运行时校验的「输入校验 / 完成判据 / 失败处理」以此为准；
③ `run.py`（或 `index.ts`）：实现入口。
约定 `SKILL.md` 只写「是什么 + 什么时候用 + 入口在哪」，字段与判据全部留在 `README.md`，禁止两处分别维护同一口径（防漂移）。

## 7. 数据模型要求（L1 稳定后冻结）

> 表名与字段名用英文，字段含义在 `db/schema.sql` 注释中说明。以下是必须覆盖的信息维度，具体表结构在设计评审时定稿。

| 信息对象    | 必须能回答的问题                                     |
| ------- | -------------------------------------------- |
| 话题 `topic` | 这个选题从哪来（人工 / 热点）、关键词、创建人、当前状态                |
| 任务 `task` | 属于哪个话题、走到哪一步、状态、优先级、目标平台、内容类型、选定的是哪套文案、何时选定 |
| 步骤流水 `step` | 某任务的第几步、用了哪个 Skill、输入输出、耗时、失败原因              |
| 产物 `artifact` | 产物类型（文案 / 图片 / 视频 / 报告）、文件路径、大小、属于哪一步、由哪个模型与哪个提示词版本产出       |
| 人工介入 `hitl_event` | 谁、何时、对什么动作、确认还是拒绝、当时的待执行内容快照                 |
| 版本 `version` | 每次结构变更对应的备份点（commit / tag）、变更摘要              |
| 数据指标 `metric` | 每期数据的采集口径、数值、统计周期、**采集时间**，供复盘与看板使用                   |

**R-7-01**：图片、视频等大文件不入库，只登记路径与元信息。
**R-7-02**：所有状态字段的取值必须在文档中枚举完整，禁止出现文档未列出的状态值。
**R-7-03**（S7）：产物表必须记录 `model_version` 与 `prompt_version`；提示词以文件形式入仓（不写死在代码里），保证任一产物可复现。
**R-7-04**（S6）：数据指标首版覆盖三项——**播放量 / 互动量（赞藏评合计）/ 涨粉数**；每项必须记录统计周期与采集时间，否则不同期数据不可比。
**R-7-05**（S5）：`topic` 与 `task` 为一对多关系；`topic.source` 枚举 `manual`（人工提交）/ `hotspot`（热点派生）。

## 10. 约束与红线

## 16. Skill 岗位与 README 契约索引（N004）

> 本节是 §5 与 R-L1-05~09、R-L1-12、R-L1-14 的落地索引；细节以两份文档为准，本节只做「谁在哪、干什么」的定位。

### 16.1 岗位数量结论

- **执行岗位 18 个 + 支撑件 7 个 = `.dsh/skills/` 下 25 个 skill 目录**（名册：`docs/skill-roster.md`）。
- 分布：文案线 2、视觉线 3、视频线 5、分发数据线 6、基础设施 2；支撑件 7（`artifact-recorder`、`hitl-gate`、`storyboard-validator`、`image-consistency-checker`、`publish-guard`、`task-decomposer`、`summary-writer`）。
- 命名规则：目录名 = `skill_id`（小写英文 + 连字符，与名册完全一致）；每个目录固定三件套 `SKILL.md` + `README.md` + `run.py`（或 `index.ts`），见 R-L1-20 与 §16.5。
- 首版范围：18 个岗位全部落地，但只做**单链路最小实现**；多平台批量、多模型投票、模板库、付费热点源、高级看板显式推迟。

### 16.2 每个 Skill 的统一执行流程（R-L1-07）

`取任务 → 输入校验 → 执行 → 自检 → 登记产物 → 交回编排者`

- skill 之间**不互相调用**，只由编排者或所属环节 Agent 派单（防止隐式耦合）；
- 「输入校验」不通过直接退回，不进入执行；
- 「自检」不通过按 README 的失败处理重试，超限标记「需人工」退回编排者。

### 16.3 README 契约（R-L1-05、R-L1-18）

- 每个 skill 的 `README.md` 必须按 `docs/skill-readme-contract.md` 的九段模板填写；其中**输入校验**与**完成判据**必须是机器可判定的表达式（最小词汇表：`count`、`ids_continuous`、`unique`、`in_range`、`all_resolution_equal`、`file_exists`、`non_empty`、`enum_in`、`no_auto_publish`）。
- 契约写在 README 中，并由运行时校验；校验失败必须退回（R-L1-18）。
- 目录级 README 三行起头；代码文件头注释块固定四行（`# 文件用途 / # 对应需求 / # 对应流程图 / # 维护提示`），对应 R-L1-14、R-L1-15。

### 16.4 图表交付流程（R-L2-18 补充）

`archify render <type> <json> <out.html> --quality showcase` → `archify check <out.html> --json` 必须 `ok:true` 且 `composition=pass` → 人工/截图核对。
本机 `browser-check` / `visual-check` 受 Chrome 沙箱限制时，允许用「render + check + 截图核对」替代，但必须登记为待办（当前 A-09），**不得静默跳过**。

### 16.5 Skill 目录三件套与 DSH 发现机制（R-L1-20，N005 实测）

| 文件 | 给谁看 | 作用 |
| ---- | ------ | ---- |
| `SKILL.md` | DSH 运行时 | 自动发现入口：YAML frontmatter（`name` = 目录名、`description` 含「什么时候用」）+ 简短用法正文 |
| `README.md` | 运营人员 + 运行时校验 | 九段模板（`docs/skill-readme-contract.md`），判据与字段以此为准 |
| `run.py` | 运行时 | 实现入口（或 `index.ts`） |

- 实测依据：工作区 `.dsh/skills/` 即 DSH 技能根目录；用一个探针目录（含 `SKILL.md`）验证「建即可被加载、删即消失」，验证后探针已清理。
- 因此**顶层目录名必须保持 `.dsh/skills/`**，改名会失去自动发现能力（用户 m00618 已确认保留）。
- 防漂移约定：`SKILL.md` 不重复写字段与判据，只指向同目录 `README.md`。
